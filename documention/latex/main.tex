\begin{abstract}
Niniejszy dokument stanowi instrukcję obsługi biblioteki \texttt{PUTM\_EV\_CAN\_LIBRARY}. Biblioteka została zaprojektowana dla systemów wbudowanych (STM32) oraz środowiska ROS2. Główne cechy to: statyczna alokacja pamięci, obsługa wielu rodzin STM32 (F4, G4, L4, H7) dzięki warstwie abstrakcji HAL, odbiór danych oparty na przerwaniach (Interrupt-Driven). Dokument zawiera również zbiór dobrych praktyk oraz najczęstszych pułapek sprzętowo-programowych.
\end{abstract}

\section{Integracja i Konfiguracja w CMake}

Biblioteka jest dystrybuowana jako moduł CMake. Aby użyć jej w projekcie, należy zmodyfikować główny plik \texttt{CMakeLists.txt} projektu.

\subsection{Dodawanie biblioteki do projektu}

\textcolor{warningred}{\textbf{BARDZO WAŻNE:}} Zawsze używaj słowa kluczowego \texttt{PRIVATE} lub \texttt{PUBLIC} przy linkowaniu. Dodatkowo, poprawne podlinkowanie \texttt{putm\_ev\_can} gwarantuje przekazanie definicji środowiskowych (np. \texttt{-DPUTM\_CAN\_BACKEND\_STM32}). Brak poprawnego linkowania zaowocuje błędem kompilacji: \texttt{\#error "Backend not defined! Check CMake configuration."}

\begin{lstlisting}[style=cmakestyle, caption=Podstawowa konfiguracja CMake]
# 1. Dodanie podkatalogu biblioteki
add_subdirectory(Core/Inc/PUTM_EV_CAN_LIBRARY)

# 2. Linkowanie biblioteki z twoim projektem (Zawsze uzywaj PRIVATE)
target_link_libraries(${CMAKE_PROJECT_NAME} PRIVATE
    stm32cubemx
    putm_ev_can
)
\end{lstlisting}

\subsection{Wybór konfiguracji (STM32 vs ROS2)}
System CMake automatycznie próbuje wykryć środowisko (Bare-metal STM32 vs system Linux z załadowanym ROS2). Jeśli autodetekcja zawiedzie, możesz wymusić zachowanie ręcznie.

\begin{lstlisting}[style=cmakestyle, caption=Wymuszanie konfiguracji w CMake]
# Dla STM32:
set(PUTM_CAN_BACKEND "STM32" CACHE STRING "Select backend" FORCE)

# Dla ROS2 / Linux:
set(PUTM_CAN_BACKEND "ROS2" CACHE STRING "Select backend" FORCE)
\end{lstlisting}

\section{Przygotowanie Sprzętowe (STM32CubeMX)}

To najważniejszy krok przy korzystaniu z nowych mikrokontrolerów z serii STM32G4 oraz STM32H7 (posiadających peryferium \textbf{FDCAN}). 

\textcolor{warningred}{\textbf{ZAKAZ:}} Nie zostawiaj domyślnych ustawień dla FDCAN w CubeMX. FDCAN, w przeciwieństwie do starszego bxCAN (z serii F4), \textbf{wymaga ręcznej alokacji pamięci RAM dla buforów FIFO!} Jeśli tego nie zrobisz, sprzęt odrzuci każdą ramkę do wysłania bez wieszania programu (tzw. "cichy błąd").

\subsection{Obowiązkowa Konfiguracja FDCAN w CubeMX}
W zakładce FDCAN1/FDCAN2 $\rightarrow$ Parameter Settings należy ustawić:
\begin{itemize}
    \item \textbf{Tx FIFO/Queue Mode:} \texttt{Tx FIFO operation} (Bardzo ważne!)
    \item \textbf{Tx FIFO/Queue Elmts Nbr:} \texttt{8} (lub inna wartość $>0$. Ustawienie $0$ oznacza brak pamięci do wysyłania!).
    \item \textbf{Rx FIFO0 Elmts Nbr:} \texttt{8} (Wymagane do odbioru z powiadomieniami).
    \item \textbf{Auto Retransmission:} \texttt{DISABLE}. Włączenie tej funkcji może doprowadzić do zapchania magistralii.
\end{itemize}

\section{Poprawna Inicjalizacja Oprogramowania}

Biblioteka przejmuje całkowitą kontrolę nad peryferium CAN. Inicjalizuje filtry, aktywuje powiadomienia o przerwaniach i fizycznie uruchamia magistralę.

\subsection{Krok 1: Instancje Globalne}
W pliku \texttt{main.cpp} (lub pliku obsługującym konkretne zadanie FreeRTOS, np. \texttt{communication\_task.cpp}) należy utworzyć obiekty dla wykorzystywanych magistral bez słowa \texttt{extern}, jeśli definicja znajduje się w tym samym pliku.

\begin{lstlisting}
// Wlasciwa definicja obiektu w pliku .cpp
putm_ev_can::CanDriver can_m; 
\end{lstlisting}

\subsection{Krok 2: Wywołanie Init() i Ciche Błędy}
\textcolor{warningred}{\textbf{ZAKAZ PODWÓJNEJ INICJALIZACJI:}} Nie wolno wywoływać funkcji \texttt{HAL\_FDCAN\_Start()} oraz \texttt{HAL\_FDCAN\_ActivateNotification()} z poziomu pliku \texttt{main.c}! 
Biblioteka wewnątrz metody \texttt{can\_m.Init(\&hfdcan1)} sama to robi. Jeśli wywołasz Start sprzętowy przed biblioteką, funkcja \texttt{Init()} zwróci błąd (status \textit{BUSY}), flaga wewnętrzna biblioteki pozostanie w stanie \textit{uninitialized}, a funkcja \texttt{Send()} nigdy nie wyśle ramki.

\textbf{Dobra Praktyka (Poprawny kod):}
\begin{lstlisting}
/* USER CODE BEGIN 2 */
// Tylko konfiguracja filtrow (jesli potrzebna)
FDCAN_FilterTypeDef filter_config;
// ... ustawienia filtra ...
HAL_FDCAN_ConfigFilter(&hfdcan1, &filter_config);

// ZADNYCH HAL_FDCAN_Start() TUTAJ! Zostaw to bibliotece.
/* USER CODE END 2 */

// ... pozniej, w tasku lub przed petla glowna ...
void Communication_Task(void* argument) {
    // 1. To wystarczy do uruchomienia komunikacji
    if (!can_m.Init(&hfdcan1)) {
        // Blad inicjalizacji (np. zablokowany sprzet)
        Error_Handler(); 
    }
    // ...
}
\end{lstlisting}

\section{Wysyłanie (TX) i Odbieranie danych (RX)}

\subsection{Odbieranie poprzez Callbacki (Interrupt-Driven)}
Odbiór w nowej wersji biblioteki działa asynchronicznie.
\textcolor{warningred}{\textbf{UWAGA:}} Kod wewnątrz callbacku wykonuje się w \textbf{KONTEKŚCIE PRZERWANIA SPRZĘTOWEGO (ISR)}.

\textbf{ZAKAZY wewnątrz Callbacku:}
\begin{itemize}
    \item Nie używaj funkcji blokujących (np. \texttt{osDelay}, \texttt{HAL\_Delay}).
    \item Nie wykonuj ciężkich obliczeń matematycznych.
    \item Nie wywołuj funkcji typu \texttt{printf}.
\end{itemize}

\textbf{Dobra Praktyka:} Zmieniaj stan zmiennych oznaczonych jako \texttt{volatile}, odświeżaj watchdoga lub używaj \texttt{osMutexAcquire(..., 0)} (czas oczekiwania $0$ dla przerwań!).

\begin{lstlisting}[caption=Rejestracja callbacku i bezpieczne operacje]
// Rejestracja musi odbyc sie tylko raz!
can_m.RegisterCallback<PUTM_CAN_M_front_data_t>(
    PUTM_CAN_M_FRONT_DATA_FRAME_ID, 
    [](const PUTM_CAN_M_front_data_t& front_data) {
        
        HAL_IWDG_Refresh(&hiwdg); // Szybka, dozwolona operacja w ISR

        // Blokada mutexa z czasem = 0 (aby nie zablokowac przerwania)
        if (osMutexAcquire(dataMutexHandle, 0) == osOK) {
            data.brake_light = front_data.is_braking;
            osMutexRelease(dataMutexHandle);
        }
    }
);
\end{lstlisting}

\subsection{Wysyłanie Danych}
Metoda \texttt{Send} sprawdza typ i bezpiecznie umieszcza ramkę w kolejce (dlatego konfiguracja FIFO w CubeMX była tak kluczowa).

\begin{lstlisting}
// Przyklad w pętli for(;;)
PUTM_CAN_M_rearbox_temperature_t temp_msg = {
    .mono_temperature = (uint8_t)temperature.mono,
    .coolant_temperature_in = (uint8_t)temperature.coolant_in,
    .coolant_temperature_out = (uint8_t)temperature.coolant_out,
    .oil_temperature_l = (uint8_t)temperature.oil_l,
    .oil_temperature_r = (uint8_t)temperature.oil_r
};

// Dobrą praktyką jest weryfikacja czy ramka została dodana do kolejki
if (!can_m.Send(PUTM_CAN_M_REARBOX_TEMPERATURE_FRAME_ID, temp_msg)) {
    // np. zapal czerwoną diodę błędu na układzie TCA.
}
\end{lstlisting}

\section{Rozwiązywanie Problemów i Znane Pułapki (FAQ)}

Poniżej zestawiono najczęściej spotykane problemy, objawy oraz rozwiązania sprzętowo-programowe.

\subsection{Pułapki Software'owe}
\begin{itemize}
    \item \textbf{Objaw:} Kod się wykonuje, ale ramki nie wychodzą na zewnątrz (\texttt{Send} zwraca błąd).
    \begin{itemize}
        \item \textbf{Przyczyna 1:} W CubeMX nie zdefiniowano rozmiaru kolejek FDCAN (\texttt{Tx FIFO/Queue Elmts Nbr} równe $0$).
        \item \textbf{Przyczyna 2:} Przedwczesne uruchomienie sprzętu przez \texttt{HAL\_FDCAN\_Start()} przed zainicjowaniem biblioteki.
    \end{itemize}
    \item \textbf{Objaw:} Błąd w CMake "Backend not defined".
    \begin{itemize}
        \item \textbf{Przyczyna:} Brak podlinkowania biblioteki do targetu przez \texttt{target\_link\_libraries(... PRIVATE putm\_ev\_can)}.
    \end{itemize}
\end{itemize}

\subsection{Pułapki Sprzętowe (Hardware)}
\begin{itemize}
    \item \textbf{Objaw:} Brak sygnału na magistrali widocznego na oscyloskopie, lub jest on całkowicie niezrozumiały/zniekształcony, a debugowanie oprogramowania nie przynosi efektu.
    \begin{itemize}
        \item \textbf{Przyczyna:} Magistrala CAN jest niezamknięta. \textbf{Brak rezystorów terminujących 120~$\Omega$ (Ohm) pomiędzy pinami CAN\_H oraz CAN\_L.} Sieć CAN działa w oparciu o różnicę napięć i wymaga fizycznego "ściągnięcia" linii do stanu recesywnego. Podczas testów "na biurku" upewnij się, że Twój sprzętowy analizator CAN ma wbudowany rezystor, lub dodaj go "na krótko" we wtyczce.
    \end{itemize}
    \item \textbf{Objaw:} Transiwer CAN się nie odzywa.
    \begin{itemize}
        \item \textbf{Przyczyna:} Pin \texttt{STBY} transiwera CAN nie jest ściągnięty do masy (GND). Zweryfikuj, czy odpowiednie rezystory konfiguracyjne zostały wlutowane na PCB.
    \end{itemize}
\end{itemize}
